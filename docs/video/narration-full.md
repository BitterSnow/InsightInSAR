## 第一部分 系统介绍与运行环境

Insight InSAR 是一个面向形变监测场景的一站式处理系统。  
它将复杂的 InSAR 流程拆成三层：桌面交互层、后端调度层、WSL 计算层。  
这样做的目的，是让用户在 Windows 上获得友好的操作体验，同时继续使用 Linux 生态里成熟的 InSAR 工具链。

从功能上看，这个系统主要提供三类能力。  
第一类是桌面端能力，包括任务管理、参数填写、区域选择和结果浏览。  
第二类是后端能力，包括任务提交、异步调度、状态跟踪和日志记录。  
第三类是计算能力，也就是在 WSL 内调用 ISCE2 和 MintPy 执行核心处理流程。

这里要特别强调一个设计原则。  
在这个项目中，Windows 负责交互与调度，WSL 负责算法与计算。  
也就是说，核心 InSAR 计算不在 Windows 本机直接跑，而是在 WSL 环境里运行。  
这个边界非常重要，它决定了后面的安装方式和排障思路。

推荐环境是 Windows 10 或 11，并启用 WSL2。  
打包交付时，Windows 侧由桌面程序自带运行环境，用户无需自行安装 Python。  
WSL 侧需要准备好 InSAR 计算所需环境，供系统在任务执行时调用。  
你可以把它理解为：Windows 是控制台，WSL 是计算引擎，二者协同完成整条处理链路。

如果你之前对 WSL 不熟悉，可以先记住一句话。  
WSL 就是 Windows 里的 Linux 运行环境。  
本系统借助 WSL，把 Linux 下的科学计算能力稳定地接入到 Windows 桌面工作流中。  
这也是它兼顾工程可用性和算法可用性的核心原因。

## 第二部分 软件安装

这一部分是全流程里最关键的环节。  
我们采用向导式安装，而不是让用户手工敲一长串命令。  
安装成功的关键，不在于步骤多，而在于顺序正确、文件齐全、路径关系正确。

请在同一个安装根目录下准备三项内容。  
第一项是 InSAR Desktop 主程序目录，双击其中的主程序即可运行桌面端。  
第二项是 InSAR WSL Deploy Wizard 部署向导目录，用于导入 WSL 环境并写入配置。  
第三项是 insar-wsl 镜像文件，通常名为 insar-wsl.tar，由构建机提前导出后随安装包一起交付。

这里有一个很容易被忽略但非常关键的点。  
如果缺少 insar-wsl 镜像文件，你可能还能打开桌面界面，但无法完成完整的 WSL 处理能力部署。  
也就是说，界面能开，不代表计算链路已经可用。  
为了避免后续能点按钮但任务跑不通的情况，建议安装阶段就把镜像文件准备完整。

准备好之后，请进入 InSAR WSL Deploy Wizard 目录，双击运行部署向导程序。  
向导通常会先检查 WSL 是否可用。  
检查通过后，你需要选择 insar-wsl 镜像的路径，再选择 WSL 导入目标目录。  
随后向导会自动执行导入，并检测 WSL 内的环境脚本，把安装根目录转换为 WSL 可访问的项目路径，写入运行配置文件。  
这一步的意义，是把系统运行参数固化下来，避免手工配置错误。  
配置会保存在安装目录以及本机应用数据目录中，主程序启动时会自动加载。

向导完成后，再进入 InSAR Desktop 目录，双击主程序启动。  
请注意这个先后顺序：先部署向导，再开主程序。  
如果反过来操作，常见结果是主程序能启动，但任务提交后在计算阶段失败。

再补充三个安装层面的高频注意点。  
第一，先确认 WSL2 已启用，这是基础前提。  
第二，确认三个安装要素在合理目录结构中，部署向导与主程序目录应与安装根目录保持文档约定的层级关系。  
第三，确认你确实执行过部署向导，并完成镜像导入，而不是只复制了文件夹。  
按这三个顺序排查，通常可以快速定位安装问题。

本系统还支持环境与代码分离。  
WSL 镜像主要承载 Ubuntu 以及 ISCE2 和 MintPy 运行环境，更新频率较低。  
业务代码放在 Windows 安装根目录下，由 WSL 通过挂载路径访问。  
因此日常若只更新后端脚本或 MintPy 相关代码，可以覆盖对应文件夹，无需重新导入镜像；只有环境大版本升级时才需要重新导出并导入新的镜像。

## 第三部分 软件使用

安装完成后，我们来看一遍标准使用流程。  
你可以把它记成六个动作：启动、检查、配置、提交、观察、验收。

打开主程序后，先检查连接状态和工作路径。  
这一小步非常重要，因为很多失败都不是算法问题，而是路径不可访问或环境未就绪。  
建议在每次新项目开始时都做这一步，节省后续排障时间。

根据项目需求设置输入数据路径、处理区域和相关参数项。  
这里建议遵循先最小可运行、再逐步精调的原则。  
先用一组保守参数验证链路打通，再进入精细化参数优化，这样效率更高也更稳。

任务提交后，系统会进入异步执行流程。  
桌面端负责展示状态，后端负责调度执行，WSL 负责计算处理。  
你不需要手动介入每个处理步骤，只要持续关注状态和日志即可。

如果任务运行正常，状态会按阶段推进。  
如果中途失败，请优先看错误前后的日志上下文，而不是只看最后一行报错。  
实践中，最常见的问题通常是路径映射、配置缺失或输入数据不符合预期。

任务完成后，在结果界面查看输出路径和相关成果。  
建议按项目和日期归档输出，保留参数记录与日志信息。  
这样做便于复现、对比和后续技术复盘。

第一次使用时，不要一上来就跑最大数据量。  
先跑通小样本、短流程、可验证的任务，确认全链路可用后，再扩大规模。  
这会显著降低试错成本，也更符合工程化部署的节奏。
